# PR 评审与合并规范 - GitHub 为例
> 目标
> - 30-40 分钟内掌握团队协作里最关键的 5 件事：
>   - 理解 Pull Request 在协作中的作用
>   - 知道提 PR 前应该把分支整理到什么程度
>   - 会在 GitHub 上发起 PR、提交 Review、Approve、Request changes
>   - 理解 `Merge` / `Squash and merge` / `Rebase and merge` 的差异
>   - 知道评审时到底应该看什么，而不是只看“能不能跑”

## 0. 这一篇要解决的问题

前面的教程已经把这些问题讲清楚了：

- 怎么在本地提交和分支开发
- 怎么和远端同步
- 怎么在团队里围绕主线协作
- 怎么在 fork 工作流里向上游仓库提交贡献

但只会 `push` 还不够。

真实团队协作里，改动进入主线之前，通常还要经过一个非常关键的环节：

**Pull Request 评审。**

这一步的意义不是“走流程”，而是让团队在合并前就能回答这些问题：

- 这次改动的范围是否清楚
- 有没有混进无关改动
- 风险点是否已经被看见
- 合并之后如果出问题，回滚是否清晰

所以这一篇真正要补的是：

**团队怎么把“有人改好了代码”变成“这份改动可以安全进入主线”。**

---

## 1. PR 在协作流程里到底扮演什么角色

你可以把 Pull Request 理解成：

- 一份明确的改动提案
- 一次公开的合并前检查
- 一个围绕改动范围展开讨论的入口

它不是单纯地“通知别人我写完了”，而是把这些信息集中到一起：

- 这次改了什么
- 为什么要改
- 应该基于哪条分支审
- 还有哪些风险和未决问题

所以 PR 的核心价值不是平台页面本身，而是：

**把“合并之前该被看清楚的事情”组织起来。**

如果没有这一步，团队协作很容易退化成：

- 谁先 push 谁说了算
- 改动到底为什么这样做，只能靠聊天记录追
- 出问题后才发现原来当时没人认真看过

---

## 2. 提 PR 之前，最低限度要准备到什么程度

一个质量过关的 PR，首先不是“写得多快”，而是“是否适合别人审”。

在打开 PR 之前，至少应该先做到这些：

- 分支只包含这次任务相关的改动
- 提交历史足够清楚，不混入大量无关实验
- 已经同步过较新的主线
- 本地至少做过基本验证，不把明显没跑过的改动直接丢给评审
- PR 标题和说明能让别人一眼看出目的

一个最小的提交前检查流程可以是：

```bash
git fetch origin
git rebase origin/main
git status
git log --oneline --graph --decorate --all
git diff origin/main...HEAD
```

这里最关键的不是命令本身，而是你要确认：

- 这条分支确实基于较新的主线
- 这次 PR 的差异范围是干净的
- 评审者看到的不会是一坨混杂着旧修改和临时实验的内容

换句话说：

**PR 的可评审性，本身就是作者的责任。**

---

## 3. 在 GitHub 上发起一个 PR 的最小流程

如果你已经把功能分支推到了远端，GitHub 通常会提示你可以发起 Pull Request。

最小流程通常是：

1. 进入仓库页面
2. 选择刚推送的功能分支
3. 点击 `Compare & pull request` 或从 `Pull requests` 页面新建 PR
4. 确认 base 分支和 compare 分支是否正确
5. 填写标题和说明
6. 选择 reviewer、label 或 milestone（如果团队在用）

这里最重要的不是“点哪个按钮”，而是两个判断：

- base 分支是不是你真正要合入的目标分支
- compare 分支是不是你这次任务对应的那条功能分支

如果这两个搞错了，后面的评审几乎都会失真。

PR 标题建议直接表达目的，例如：

- `feat: add login form validation`
- `fix: avoid duplicate message dispatch`
- `docs: clarify merge and rebase history`

PR 描述至少应该能回答：

- 这次为什么改
- 主要改了哪些点
- 怎么验证
- 还有什么暂时不做

## 4. GitHub 上的 Review 动作分别意味着什么

进入 PR 后，评审通常会集中在 `Files changed` 页面进行。

GitHub 上最常见的几个动作是：

- 行内评论：针对某一行或某一段具体提出问题
- `Review changes`：提交一次正式 review
- `Comment`：给意见，但不表示批准或拒绝
- `Approve`：认为这份改动可以进入下一步
- `Request changes`：要求作者先修改，再继续

你可以先把它们这样理解：

- `Comment` = 我有反馈，但这次 review 不下结论
- `Approve` = 我认为这份改动可以通过
- `Request changes` = 这里有问题，先别继续合并

要特别注意一个容易混淆的点：

**`Request changes` 在团队流程上通常表示“先别合”，但它是否真的硬性阻止 merge，还取决于仓库是否配置了分支保护规则或 ruleset。**

所以团队不能只依赖按钮状态，还要有明确共识：

- 什么情况下必须修完再合
- 什么情况下评论只是建议

## 5. 评审时真正该看什么

很多新手做 review 时，容易把注意力只放在“代码能不能运行”上。

但真正有价值的评审，通常至少要看下面这些点：

### 1. 改动边界是否清楚

- 这次 PR 是不是只解决一个相对明确的问题
- 有没有把无关重构、格式化、顺手修改混进来

### 2. 行为变化是否符合目标

- 改动是否真的解决了它声称要解决的问题
- 是否引入了新的行为回归

### 3. 风险是否可控

- 关键逻辑是否有明显边界遗漏
- 回滚是不是清楚
- 一旦出问题，能否快速定位和撤回

### 4. 历史是否适合合并

- 提交说明是否有语义
- 有没有明显应该 squash 的碎提交
- 有没有把调试提交、临时打印、无意义 rename 带进来

### 5. 可维护性是否变差

- 命名是否更清楚还是更模糊
- 逻辑是否更容易理解
- 有没有为局部方便引入长期维护成本

所以一个好 review，不是“挑格式”，而是：

**帮助团队在合并前就看见结构问题、行为风险和历史质量。**

## 6. 作者收到 review 之后应该怎么处理

PR 评审不是单向审批，而是一次协作回路。

如果收到了 review，作者通常需要做三件事：

1. 先区分哪些是必须修改的问题，哪些是讨论性建议
2. 在分支上继续提交修正
3. 必要时回复评论，说明你是如何处理的

常见流程通常是：

```bash
git add .
git commit -m "fix: address review feedback"
git push
```

GitHub 会把新提交自动追加到现有 PR 里。

如果修改已经完成，再根据团队习惯：

- 重新请求 reviewer 查看
- 或者在评论里明确说明“已按建议修改”

一个非常重要的习惯是：

**不要一边改评审意见，一边顺手塞新的无关需求进去。**

否则 PR 会越来越难审，也会让 review 记录失真。

## 7. 三种常见合并方式到底有什么差别

GitHub 上常见的合并方式通常有三种，但仓库是否开放这些选项，要看仓库设置。

### `Merge pull request`

这会创建一个 merge commit，把整条分支历史合进来。

适合：

- 想保留完整分支形状
- 这条分支本身的提交历史已经比较清楚

特点是：

- 历史最真实
- 分支结构也最明显
- 提交图可能更复杂

### `Squash and merge`

这会把整个 PR 压成一个新提交再合进主线。

适合：

- PR 内部有很多碎提交
- 团队希望主线历史更整齐

特点是：

- 主线更干净
- 但 PR 分支内部的细粒度提交不会原样保留在主线上

### `Rebase and merge`

这会把分支上的提交按顺序重放到目标分支后面。

适合：

- PR 提交本身已经足够清晰
- 团队想保持线性历史

特点是：

- 主线历史更线性
- 提交关系会被重新接到新的基线上
- 某些情况下提交 ID 会和原来分支上的表达不同

一个足够实用的判断方式是：

- 想保留完整分支历史 -> `Merge pull request`
- 想让主线最整齐 -> `Squash and merge`
- 想保留多提交但又偏好线性历史 -> `Rebase and merge`

## 8. 团队里最常见的几个坏习惯

- PR 太大，一次塞进太多无关改动
- 提 PR 前根本没同步主线
- Review 只看能不能跑，不看边界和回滚
- 收到评审意见后继续往同一个 PR 里混入新需求
- 看到 `Approve` 就机械合并，不看 CI、分支规则和剩余风险

这些问题的共同根源是：

把 PR 当成“形式上的最后一步”，而不是“合并前真正的质量关口”。

## 9. 这一篇的过关标准

如果下面这些问题你都能答清楚，就说明这一篇已经过关了：

- 为什么 PR 不是单纯的“通知别人我写完了”
- 提 PR 前为什么要先保证分支可评审
- GitHub 上 `Comment`、`Approve`、`Request changes` 分别意味着什么
- 三种合并方式分别更适合什么场景
- 一个像样的 review 应该重点看什么

下一篇就可以进入真正的版本发布问题了：

**当改动已经被评审并进入主线之后，怎样把它组织成一个可识别、可追踪、可回滚的正式版本。**
