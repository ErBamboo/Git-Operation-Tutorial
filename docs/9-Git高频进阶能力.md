# Git 高频进阶能力
> 目标
> - 30-40 分钟内掌握最常遇到的 5 组进阶能力：
>   - `stash`
>   - `cherry-pick`
>   - `tag`
>   - `restore` / `reset` / `revert`
>   - 知道哪些能力值得下一阶段继续深挖

## 0. 这一篇要解决的问题

很多人学 Git 到这个阶段，会本能想继续找更“高级”的命令。

但真实开发里，最值得优先掌握的，往往不是最炫的技巧，而是这些高频场景：

- 手头改到一半，临时要切去修别的问题
- 某个修复已经在别的分支做好了，只想搬这一条提交
- 某个稳定版本需要一个明确标记
- 某次撤销到底该改工作区、改暂存区，还是改历史

所以这一篇的目标非常务实：

**把真正常用、又最容易用错的能力讲清楚。**

---

## 1. `stash`：临时把未完成修改收起来

最常见的场景是：

- 你正在改一半
- 代码还不适合提交
- 但现在必须切去别的分支处理事情

这时就可以用：

```bash
git stash push -m "wip: parser cleanup"
git stash list
```

它的作用是：

- 先把当前工作区和暂存区里的改动收起来
- 让你回到一个更干净的状态，方便切分支

之后可以这样恢复：

```bash
git stash apply stash@{0}
```

或者直接恢复并移除该 stash：

```bash
git stash pop
```

还可以先看内容：

```bash
git stash show -p stash@{0}
```

但一定要记住一个边界：

**`stash` 适合临时切换上下文，不适合长期保存工作成果。**

如果某段修改已经有明确价值，优先考虑正式提交到分支，而不是长期塞在 stash 里。

---

## 2. `cherry-pick`：只搬你想要的那一个提交

一个非常典型的场景是：

- 你在 `feature/refactor` 上顺手修好了一个 bug
- 但现在 `release` 分支也急需这个修复
- 你不想把整个重构分支一起搬过去

这时就该用：

```bash
git log --oneline
git switch release
git cherry-pick <commit-id>
```

它的意义是：

- 只复制指定提交的修改效果
- 不要求整条分支一起合并

所以 `cherry-pick` 很适合：

- 搬运 hotfix
- 只提取某个独立修复
- 从多个实验分支里挑出最后真正想保留的提交

但它也有代价：

- 同一份逻辑可能在不同分支生成不同提交 ID
- 如果滥用，历史会显得更碎

所以判断标准可以简单记成：

- 整条线都要 -> 优先考虑 `merge`
- 只要其中一个提交 -> 考虑 `cherry-pick`

---

## 3. `tag`：给稳定版本一个正式名字

分支表示“开发线”，但很多时候你还需要表达：

**这个提交就是一个正式可识别的版本。**

这时就应该用 `tag`。

最常见的方式是：

```bash
git tag -a v1.0.0 -m "release: v1.0.0"
git tag
git show v1.0.0
```

如果要推到远端：

```bash
git push origin v1.0.0
```

它适合这些场景：

- 发布版本
- 留下比赛前、发版前、验收前的稳定点
- 给后续回溯一个明确锚点

所以不要只靠“我记得那时候大概是这个提交附近”来找版本。

有明确里程碑，就打 tag。

---

## 4. `restore`、`reset`、`revert` 最容易混，但必须分清

这三个词都带一点“撤销”的味道，所以最容易被混成一团。

你可以先按这个思路记：

### `restore`

重点是：

- 改工作区
- 改文件状态
- 不直接改历史

常见例子：

```bash
git restore note.txt
git restore --staged note.txt
```

适合：

- 撤销工作区未提交改动
- 把文件从暂存区拿回来

### `reset`

重点是：

- 可以移动 `HEAD`
- 可以改暂存区
- 也可能影响工作区

常见例子：

```bash
git reset HEAD note.txt
git reset --soft HEAD~1
git reset --hard HEAD~1
```

这里的 `HEAD~1` 沿用第 4 篇讲过的那套提交引用表达式：

- `HEAD~1` 表示沿第一父链退回当前提交的上一个提交
- `HEAD^`、`HEAD^2` 也是同一类写法，只是分别表示第一个父提交和第二个父提交
- 这类写法也可以连续组合，例如 `HEAD^^`、`HEAD^2~1`

新手至少先记住：

- `--soft`：回退提交，但保留改动
- `--hard`：提交、暂存区、工作区一起回退

所以 `reset --hard` 一定要谨慎，它真的会丢当前未保留的工作区状态。

### `revert`

重点是：

- 不抹掉旧历史
- 新增一个“反向提交”来撤销之前的效果

常见例子：

```bash
git revert <commit-id>
```

它特别适合：

- 已经推到远端的公共历史
- 团队协作里需要安全撤销某次错误提交

你可以把这个判断规则记死：

- **公共历史要撤销，优先想 `revert`**
- **私有历史想重整，可以考虑 `reset`**
- **只是想改工作区或暂存区，优先想 `restore`**

## 5. 一个最实用的场景对照表

| 你现在的需求 | 更合适的工具 |
|---|---|
| 临时收起没做完的修改，待会再回来 | `stash` |
| 只把某个修复搬到另一条线 | `cherry-pick` |
| 给稳定版本打标记 | `tag` |
| 撤销工作区里一个文件的改动 | `restore` |
| 取消暂存 | `restore --staged` 或 `reset HEAD <file>` |
| 回退本地未发布历史 | `reset` |
| 安全撤销已经推到远端的提交 | `revert` |

如果你能按场景选工具，而不是按感觉乱试，Git 的误操作会少很多。

---

## 6. 下一阶段最该补齐什么

到这里，Git 的日常工作流已经比较完整了。

下一阶段最自然的重点，不再是继续堆单个命令，而是把团队落地流程补完整：

1. PR 评审与合并规范
2. 轻量发布流与版本发布

原因很简单：

- 到这里你已经会改代码、同步远端、协作分支、提交贡献
- 接下来更关键的问题是：改动怎么进入主线，主线又怎么变成正式版本

所以更推荐的下一步顺序是：

1. 先学 PR 评审与合并规范
2. 再学轻量发布流与版本发布
3. 之后再回头继续深挖 `reflog`、交互式 rebase、`bisect`

这样理解会更自然：先把“团队怎么接纳改动”学清楚，再把“团队怎么发布版本”学清楚。

---

## 7. 这一篇的过关标准

如果下面这些问题你都能答清楚，这一阶段基本就闭环了：

- 什么时候该用 `stash`，什么时候不该
- 为什么 `cherry-pick` 适合搬单个修复
- 为什么稳定版本需要 `tag`
- `restore`、`reset`、`revert` 分别在改哪一层
- 为什么公共历史撤销时更应该想到 `revert`

学到这里，你的 Git 认知就已经不再只是“会几个命令”，而是已经有了一套比较完整的本地、远端、协作、并行和回退工作流。

下一篇，就该进入真正的团队协作质量控制环节了：

**当一条分支上的代码已经写完，团队应该怎样通过 Pull Request 把它评审、讨论并安全合入主线。**
