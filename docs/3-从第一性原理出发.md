# Git —— 从第一性原理出发

第 2 篇解决的是一个问题：

- 为什么需要 Git

这一篇要解决的是另一个更底层的问题：

- Git 本质上到底在管理什么

如果这一层没有想清楚，后面学命令时就会一直有一种感觉：

- 这个命令记住了
- 那个命令也会写了
- 但整体上还是像在背口诀

所以这一篇不是命令篇，而是整套教程的中枢篇。

它的作用是先建立一个最小模型，然后告诉读者：

- 第 4 篇先练本地
- 第 5 篇引入远端
- 第 6、7 篇是在前面的基础上继续加对象、加关系

如果只讲第一性原理，Git 本质上只做四件事：

- 记录某一时刻项目长什么样，也就是保存快照
- 用父子关系把这些快照连成历史
- 用引用去标记“当前哪条线走到了哪里”
- 在不同仓库之间同步这些对象和引用

后面看起来很复杂的命令，基本都只是围绕这四件事展开。

---

## 1. Git 在管理什么

从第一性原理看，Git 并不直接管理“命令”，它管理的是一组对象和它们之间的关系。

最小模型可以先画成这样：

```text
+--------------------------------------------------+
| 第1层：工作区                                    |
| 你眼前正在编辑的文件                             |
+--------------------------------------------------+
                       |
                       | git add / git restore
                       v
+--------------------------------------------------+
| 第2层：暂存区                                    |
| 下一次提交准备带走的内容                         |
+--------------------------------------------------+
                       |
                       | git commit
                       v
+--------------------------------------------------+
| 第3层：本地对象库                                |
| 提交对象: A---B---C                              |
| 分支引用: main -> C                              |
| HEAD:     HEAD -> main                           |
+--------------------------------------------------+
                       |
                       | git fetch / git push / git pull
                       v
+--------------------------------------------------+
| 第4层：远端相关对象                              |
| 远端跟踪引用: origin/main -> C                   |
| 远端仓库中的 main 也指向 C                       |
+--------------------------------------------------+
```

这张图已经足够解释后面大多数 Git 行为。

这里最关键的对象有 7 个：

- 工作区：你正在编辑的文件
- 暂存区：下一次提交准备放进去的内容
- 提交对象：某一时刻项目的完整快照
- 分支引用：例如 `main`，本质上是“指向某个提交的名字”
- `HEAD`：当前检出位置。多数时候它先指向当前分支，当前分支再指向最新提交
- 远端跟踪引用：例如 `origin/main`，表示“你当前已知的远端 main 在哪里”
- 远端仓库：另一份对象和引用的集合

所以，Git 从来不只是“帮你存几个版本”。

它真正管理的是：

- 项目的状态
- 状态之间的历史关系
- 哪些名字在指向这些状态
- 不同仓库之间这些对象如何同步

---

## 2. “第一性原理”

所谓第一性原理，不是把概念讲得更抽象，而是把复杂现象还原到最少的底层事实。

对 Git 来说，后面会遇到的很多问题：

- 为什么 `commit` 和工作区不是一回事
- 为什么分支不是复制一份代码
- 为什么 `rebase` 会改历史
- 为什么 `fetch` 不会直接改本地分支
- 为什么 `push` 失败时会说 non-fast-forward

它们表面上看是不同问题，但底层都可以落回同一个模型：

- 工作区变了没有
- 暂存区变了没有
- 有没有新提交对象产生
- 哪个引用移动了
- 哪个远端引用和本地引用没有对齐

这就是这一篇的意义：

**先把底层对象和关系搞清楚，后面的命令就不再像孤立技巧，而会变成一套可解释的状态变化。**

---

## 3. 先看“纵向”：单个仓库内部怎么流转

整套教程会先从简单到复杂展开。

第一步先只看一个仓库内部，也就是先看“纵向流转”。

所谓“纵向”，指的是：

- 不先引入远端
- 不先引入协作
- 只看一个仓库内部，内容如何从工作区一路进入正式历史

这条最基本的流转线是：

```text
+-----------------------------+
| 工作区                      |
| 还在编辑、还可能继续变化    |
+-----------------------------+
              |
              | git add
              v
+-----------------------------+
| 暂存区                      |
| 决定下一次提交要装什么      |
+-----------------------------+
              |
              | git commit
              v
+-----------------------------+
| 提交对象                    |
| 已进入正式历史              |
+-----------------------------+
```

所以第 4 篇为什么先从本地练习开始，原因很简单：

- 因为这是最基础、最稳定的一层
- 如果这条线还没看清，再叠加远端、协作、fork，只会越来越乱

第 4 篇要练的，本质上就是这一层：

- 工作区怎么进入暂存区
- 暂存区怎么生成提交
- 分支和 `HEAD` 在单仓库内部怎么移动

---

## 4. 再看“引用”：为什么分支不是副本

很多新手一开始最容易误解的，是把分支理解成“复制出一份代码”。

从第一性原理看，分支不是副本，而是引用。

例如：

```text
初始状态：

提交历史: A---B---C
分支引用: main -> C
HEAD:     HEAD -> main

创建并切换到 feature/theme 后：

提交历史: A---B---C
分支引用: main -> C
         feature/theme -> C
HEAD:     HEAD -> feature/theme

feature/theme 上产生新提交后：

提交历史: A---B---C---D
分支引用: main -> C
         feature/theme -> D
HEAD:     HEAD -> feature/theme
```

这里发生的事情只有两类：

- 新建了一个分支引用
- 后来又让这个分支引用指向了更新的提交

代码没有被复制一份，真正变化的是“哪一个名字在指向哪一个提交”。

所以：

- 分支很便宜，因为新建分支通常只是增加一个引用
- 切换分支也不是“切换到另一份仓库”，而是让 `HEAD` 站到另一条引用上

这也是为什么第 4 篇里会先讲“切出分支”的含义。

因为如果不先理解引用，后面的 `merge`、`rebase`、`worktree` 都会显得很神秘。

---

## 5. 再加一层：为什么 Git 不只关心本地

如果只看本地三层结构，这当然还不够支撑整套教程。

因为 Git 不是单机笔记本，它天生还要处理另一类问题：

- 我本地知道的远端状态是什么
- 远端主线和本地主线谁更新
- 哪些提交只是本地有，哪些提交远端也有

所以在本地模型之外，还要再加一层“远端相关对象”：

```text
+--------------------------------------+
| 本地对象库                           |
| 提交对象: A---B---C                  |
| main -> C                            |
| HEAD -> main                         |
+--------------------------------------+
                  |
                  | 记录 / 同步
                  v
+--------------------------------------+
| 远端相关对象                         |
| origin/main -> C                     |
| 远端仓库里的 main 也指向 C           |
+--------------------------------------+
```

这里最重要的一点是：

**Git 在同步时，同步的不是“一个文件夹”，而是提交对象和引用。**

所以第 5 篇学 `fetch`、`pull`、`push` 时，真正要观察的不是“文件有没有刷新”，而是：

- `origin/main` 有没有前进
- 本地 `main` 有没有前进
- 远端的分支指针有没有被推上去

一旦把这一层加进来，后面的“领先 / 落后 / 分叉”就不再只是术语，而会变成引用关系。

## 6. 继续做加法：进入协作和 fork

到这里为止，模型已经有了两层：

- 单仓库内部的纵向流转
- 本地与远端之间的横向同步

后面继续学，并不是推翻前面的模型，而是在这个模型上继续做加法。

### 第 6 篇：多人围绕同一个远端协作

会新增的问题是：

- 主线和功能分支之间怎么整合
- 别人推进了 `origin/main`，我的功能分支怎么办
- 为什么同样是“接上主线”，有时用 `merge`，有时用 `rebase`

但它们仍然没有跳出当前模型，只是额外增加了：

- 更多分支引用
- 更多提交关系
- 更多“谁该向谁对齐”的判断

### 第 7 篇：fork / upstream 工作流

这一步再加的，不是新的 Git 哲学，而是新的仓库关系：

- `origin` 不再是主仓库
- `upstream` 成为真正的同步来源
- 本地、个人 fork、上游仓库之间形成三层关系

所以第 7 篇本质上是在第 5 篇“本地 <-> 远端”的基础上，再增加一个远端角色。

---

## 7. 整套教程这样安排

这一套教程是按下面这个顺序展开的：

1. 先回答“为什么要用 Git”
2. 再回答“Git 本质上在管理什么”
3. 然后只练一个仓库内部最基础的纵向流转
4. 再加入远端，开始横向理解同步
5. 再加入多人协作
6. 最后再加入 fork / upstream、并行开发、评审和发布流

这就是整套教程背后的组织方式：

- 从简单到复杂
- 从纵向到横向
- 逐渐做加法

所以后面出现的新概念，并不是在推翻前面，而是在前面的模型上再加一层：

- 第 4 篇加本地练习
- 第 5 篇加远端同步
- 第 6 篇加多人协作
- 第 7 篇加多远端角色

如果把这个顺序记住，后面就不会有“为什么突然多出这么多命令”的感觉。

---

## 8. 结尾

学完这一篇，最重要的不是背会一句定义，而是留下这几个稳定认知：

- Git 管理的是对象和关系，不是命令本身
- 单仓库内部先看工作区、暂存区、提交对象、分支、`HEAD`
- 远端同步本质上是在同步提交对象和引用
- 后面的章节不是推翻前面的理解，而是在同一个模型上继续做加法

如果这几个认知稳定了，后面的学习体验会完全不同：

- 第 4 篇不再只是练命令，而是在练“纵向流转”
- 第 5 篇不再只是学远端，而是在学“横向同步”
- 第 6、7 篇也不再只是多几个术语，而是在原模型上加分支关系和仓库关系

下一篇，就进入这套模型里最简单、也最重要的一层：

**先只看一个本地仓库内部，怎么从工作区一路走到正式提交。**
