# 轻量发布流与版本发布
> 目标
> - 30-40 分钟内掌握轻量发布流里最关键的 5 件事：
>   - 理解 `tag` 在发布场景里到底扮演什么角色
>   - 知道轻量发布流和复杂发布模型的边界
>   - 会组织一个最小可执行的版本发布流程
>   - 知道 release note 至少应该记录什么
>   - 明白版本号、回滚点和热修复之间的关系

## 0. 这一篇要解决的问题

在第 9 篇里，`tag` 已经作为一个常用能力出现过了。

但那个位置解决的是：

- `tag` 是什么
- 什么时候能用它
- 基本命令怎么写

而真正进入团队落地时，你会碰到的是另一类问题：

- 什么样的提交才算一个正式版本
- 版本号应该什么时候增加
- 发版记录应该怎么留
- 如果线上出问题，回滚点在哪里

这时，`tag` 就不再只是一个命令，而是版本发布流程里的核心锚点。

所以这一篇真正要讲的是：

**怎样用最轻量、最容易落地的方式，把主线上的稳定状态组织成正式版本。**

---

## 1. 什么叫“轻量发布流”

这里说的轻量发布流，不是完整的 Git Flow，也不引入额外的 `develop`、`release/*` 长期分支。

它的最小模型通常只有这些东西：

- 一条可信的主线，通常是 `main`
- 一个明确的版本号，例如 `v1.2.0`
- 一个指向发布点的 annotated tag
- 一份能说明本次版本变化的 release note

你可以把它理解成：

- `main` 负责表达当前可持续演进的主线
- `tag` 负责把某个稳定提交标记成“正式版本”
- release note 负责告诉别人“这个版本包含了什么变化”

这套模型的好处是：

- 规则简单
- 上手成本低
- 很适合当前这套教程的学习阶段

---

## 2. `tag` 在发布语境里到底是什么

平时我们说 `tag`，很容易只把它理解成“给提交起个名字”。

但在发布语境里，它更准确的作用是：

- 给一个正式版本钉下锚点
- 让你之后能明确回到“就是这个版本”
- 让发布记录和代码状态建立稳定对应关系

这也是为什么版本发布一般更推荐 annotated tag：

```bash
git tag -a v1.2.0 -m "release: v1.2.0"
```

因为它不只是一个轻量名字，还能附带：

- tag 名称
- 创建者信息
- 时间
- 说明文字

所以在版本发布里，`tag` 不应该被当成可有可无的装饰，而应该被看成：

**版本管理里最清晰的定位点。**

---

## 3. 一个提交什么时候才适合被发布

不是所有 `main` 上的最新提交都应该立刻发版。

在打 tag 之前，至少应该先确认这些事情：

- 这批改动已经完成基本评审
- 主线状态相对稳定，不是半完成状态
- 已知阻塞问题已经被处理或明确记录
- 版本范围清楚，知道这次到底准备发布什么

也就是说，发版不是“有人刚合完代码就顺手打一版”，而是：

**你确认主线上的某个状态，已经足够被外部识别、复现和回溯。**

如果这一步不做判断，后果通常会很直接：

- 版本号打得很多，但没人知道每个版本代表什么
- 出问题时找不到可信的回滚点
- 发布记录和真实代码状态脱节

---

## 4. 版本号应该怎么想

这里不展开完整的版本规范，只先建立一个够用的最小理解：

- `v1.2.3`
- `1` = 重大变化
- `2` = 向后兼容的新功能
- `3` = 向后兼容的问题修复

你不一定要在当前阶段把版本号体系做得很复杂，但至少要做到：

- 版本号是有顺序的
- 每次发布都能明确知道是增了哪一层
- 团队对“什么算 patch / minor / major”有基本共识

对于多数教学项目或小团队，先从这种最简单的规则开始就够用了：

- 修 bug -> 补丁号增加
- 加功能但不破坏旧用法 -> 次版本号增加
- 改动会影响旧使用方式 -> 主版本号增加

---

## 5. 一个最小可执行的发布流程

如果你只想先把发布流跑通，下面这一套已经够用。

### 第一步：回到主线并同步最新状态

```bash
git switch main
git pull --ff-only
```

### 第二步：确认本次版本范围

这一步至少要回答：

- 这次准备发布的是哪个阶段成果
- 上一个版本之后改了什么
- 有没有明显不该进入这次版本的内容

常见做法可以先从这两个命令开始：

```bash
git tag
git log --oneline --graph --decorate --all
```

如果你已经有上一个版本 tag，还可以看两次版本之间的提交：

```bash
git log --oneline <old-tag>..HEAD
```

### 第三步：打 annotated tag

```bash
git tag -a v1.2.0 -m "release: v1.2.0"
git show v1.2.0
```

### 第四步：把主线和 tag 推上远端

```bash
git push origin main
git push origin v1.2.0
```

### 第五步：记录 release note

release note 不一定一开始就很复杂，但至少应该写清楚：

- 这个版本做了什么
- 修了哪些关键问题
- 有没有需要特别注意的变化

如果仓库托管在 GitHub 上，还可以基于 tag 再创建一个 Release 页面；但这一步是发布记录的补充，不是替代 tag。

---

## 6. release note 至少应该记录什么

很多团队的问题不是“不会打 tag”，而是：

打完 tag 之后，没有人说得清这个版本到底包含了什么。

所以一份最小可用的 release note，至少应该有这几类信息：

- 版本号
- 发布时间
- 本次新增内容
- 本次修复内容
- 已知限制或注意事项

如果你想写得更清楚，可以继续加：

- breaking changes
- 升级建议
- 关联的 PR 或 issue

release note 的作用不是写得好看，而是让后来的人能快速回答：

**这个版本到底是什么、改了什么、遇到问题该从哪里查。**

---

## 7. 轻量发布流里怎么处理热修复

最常见的热修复场景是：

- 某个已发布版本出了问题
- 你需要尽快发一个补丁版本

在最简单的情况下，如果 `main` 仍然接近当前线上版本，那么流程通常可以是：

1. 从 `main` 或当前稳定点切出修复分支
2. 修问题并走最小评审流程
3. 合回主线
4. 打一个补丁版本 tag，例如从 `v1.2.0` 到 `v1.2.1`

也就是说，热修复的关键不是“单独发明一套流程”，而是：

- 修复范围要小
- 回滚点要清楚
- 版本号要能表达“这是基于上个稳定版本的小修复”

如果主线已经积累了大量尚未准备发布的变化，那就说明你已经逐步碰到了更复杂的发布管理问题。那时才值得进一步学习更完整的 release / hotfix 分支策略。

---

## 8. 最常见的几个发布坏习惯

- 只打 tag，不留任何版本说明
- 主线还没稳定就急着发版
- 版本号随手乱加，没有一致规则
- 发版后不把 tag 推到远端
- 出问题时才发现没有清晰的上一个稳定锚点

这些问题的共同根源是：

把发布理解成“最后多敲一条命令”，而不是“把一个稳定状态正式命名并留下记录”。

---

## 9. 这一篇的过关标准

如果下面这些问题你都能答清楚，就说明这一篇已经过关了：

- 为什么 `tag` 在发布语境里不是可有可无的
- 一个提交什么时候才适合被正式发布
- 一个最小发布流程里为什么必须有版本号、tag 和 release note
- 热修复为什么通常应该体现为补丁版本递增
- 为什么发布流的重点不是命令，而是“正式版本锚点”和“可追踪记录”

学到这里，你对 Git 的理解就已经从“如何管理修改”进一步走到了“如何让团队协作结果被稳定发布和持续追踪”。
