# 协作开发主流程
> 目标
> - 30-40 分钟内掌握团队协作中最核心的 5 件事：
>   - 围绕主线开功能分支
>   - 在协作前先同步远端状态
>   - 理解什么时候用 `merge`
>   - 理解什么时候用 `rebase`
>   - 知道冲突出现时应该怎么处理

---

## 0. 这一篇真正要解决的问题

学完远端基础之后，真正的难点通常不是“命令不会写”，而是：

- 我应该从哪条线开始做功能
- 别人已经往主线推了新提交，我该怎么同步
- 两个人都改了，我到底是该 `merge` 还是 `rebase`
- 冲突出现之后，我接下来应该做什么

所以这一篇的重点不是堆更多命令，而是建立一个简单但可靠的协作主流程。

先给出推荐版本：

1. 先同步主线
2. 从主线切出功能分支
3. 在功能分支上独立提交
4. 需要同步主线时，再把主线整合进来
5. 功能完成后，再把功能分支合回主线

如果你把这 5 步变成习惯，多数日常协作问题都会大幅减少。

---

## 1. 推荐工作流：始终围绕主线开功能分支

假设你要开始做一个功能，最稳妥的起手式通常是：

```bash
git switch main
git fetch origin
git pull --ff-only
git switch -c feature/login
```

这几步分别在做什么：

- 回到主线
- 确认远端主线有没有新变化
- 把本地主线快进到最新
- 从最新主线切一条功能线出来

这背后的原则是：

**功能开发应该围绕“最新且可信的主线状态”开始，而不是围绕你几天前留下的某个旧分支开始。**

接下来你就在功能分支上正常提交：

```bash
git add .
git commit -m "feat: add login form"
git push -u origin feature/login
```

这里要有一个稳定认知：

- `main` 负责表达稳定主线
- `feature/*` 负责表达某个独立功能或任务

不要把所有事情都塞进 `main`，也不要把所有零碎实验都混在同一条功能分支里。

---

## 2. 当主线前进了，你该怎么同步

最常见的协作场景是：

- 你正在 `feature/login` 上工作
- 别人已经把新的提交推到了 `main`

这时正确的第一步不是盲目 `pull`，而是先看清远端发生了什么：

```bash
git fetch origin
git log --oneline --graph --decorate --all
```

然后你再决定怎么把 `origin/main` 的变化整合进当前分支。

最常见的两种方式是：

```bash
git merge origin/main
```

或者：

```bash
git rebase origin/main
```

它们都能让你“接上最新主线”，但侧重点不同。

---

## 3. 初学阶段怎么理解 `merge` 和 `rebase`

先不要把它们神秘化。

### `merge`

你可以把 `merge` 理解成：

- 保留两条线各自的历史
- 新建一个“整合结果”的提交

它的优点是：

- 历史真实
- 不改已经存在的提交
- 对共享分支更安全

它的代价是：

- 历史图会更复杂一些

### `rebase`

你可以把 `rebase` 理解成：

- 把你这条线上的提交“搬到新的基底上重放一遍”

它的优点是：

- 历史更线性
- 你本地看起来更整齐

它的代价是：

- 会重写提交历史

所以给新手一个足够实用的判断标准：

- **如果这是你自己单独使用的功能分支，想接上最新主线，可以优先用 `rebase`**
- **如果这是多人共同维护的共享分支，优先用 `merge`**

原因很简单：

- 个人分支重写历史，影响范围小
- 共享分支重写历史，容易让别人同步时混乱

## 4. 冲突不是 Git “坏掉了”，而是 Git 在要求你做决定

冲突出现时，很多新手会慌。其实你应该先理解：

**冲突说明两边都对同一块内容做了修改，而 Git 无法替你判断哪一个才是你真正想保留的结果。**

这不是异常情况，而是正常工程判断。

一个常见流程是：

```bash
git fetch origin
git rebase origin/main
```

如果中途出现冲突，Git 会停下来。

这时你的处理步骤通常是：

1. 打开冲突文件，看懂两边改了什么
2. 手工改成你真正想要的最终结果
3. 把冲突文件重新加入暂存区
4. 继续当前操作

如果你走的是 `rebase` 流程，对应命令通常是：

```bash
git add <file>
git rebase --continue
```

如果你想放弃本次 rebase：

```bash
git rebase --abort
```

如果你走的是 `merge` 流程，那么解决完冲突并 `git add` 之后，通常再做一次提交即可。

你要建立的观念不是“别出现冲突”，而是：

**冲突出现时，我知道该先看内容，再决定怎么整合。**

## 5. 一个足够可靠的日常协作模板

如果你不想每次都临场思考，下面这个模板可以直接记住：

### 开始功能前

```bash
git switch main
git fetch origin
git pull --ff-only
git switch -c feature/<task-name>
```

### 功能开发中

```bash
git add .
git commit -m "feat: ..."
git push -u origin feature/<task-name>
```

### 主线有更新时

```bash
git fetch origin
git rebase origin/main
```

如果这条功能分支是多人共享，就改成：

```bash
git fetch origin
git merge origin/main
```

### 功能完成后

- 提交干净、语义清晰的历史
- 确认分支已经基于较新的主线
- 再进入合并、提 PR 或团队评审流程

---

## 6. 协作开发最常见的几个坏习惯

- 在 `main` 上直接长期开发
- 明明没看远端状态，却先 `pull`
- 多人共享分支却反复 `rebase`
- 冲突一出现就想“用一个版本把另一个全覆盖”
- 提交说明全写成 `update`、`fix bug`、`改一下`

这些习惯的共同问题是：

它们都在削弱 Git 帮你维持“开发秩序”的能力。

## 7. 这一篇学完后，你真正应该会的不是命令，而是判断

如果你已经能稳定回答这些问题，就说明这篇过关了：

- 为什么功能开发应该从最新主线切出去
- 为什么协作前先 `fetch` 比直接 `pull` 更稳
- 什么情况下 `rebase` 更合适
- 什么情况下 `merge` 更安全
- 冲突出现时，为什么第一步是看文件内容而不是乱按命令
