#                            电控组Git工具入门指南



## 一、前言

​	**<!--照例，每篇文档开头会有一段前言，用于交代本指南写作背景与目的。-->**

​	**众所周知，醒狮战队虽然拥有自己的代码仓库，各兵种也拥有各自的分支，但显然其在日常开发中的作用并不显著。截止该文档撰写之日（2025年7月1日），一方面，各兵种最多有一份车组代码，且仅由1-2名正队进行开发和维护；另一方面，队内并不像其他高校（如湖南大学）那样一套需要统一维护的框架，确实没有必要大费周章地进行全电控组统一的代码管理。因此，多数人内心处于一种”知道这个东西有用，但不知道有什么用，如何用“的境地，进一步地会产生”这个东西有点麻烦，用微信压缩包传来传去也能用”的想法，这无可厚非。**

​	**然而，隐藏在“够用”的背后，实际上已经暴露出代码不统一、无管理的弊端了。例如：25赛季接近完整形态考核，笔者和另一位电控师兄解决了遗留已久的底层串口驱动问题，但该问题的解决仅引起部分人关注，多数队员不关心为什么有问题以及如何解决的。待到25赛季区域赛开赛期间，仍然有兵种的代码保留了旧的串口驱动，以至于排查问题时成为了一个干扰项。再例如：一个车组内若多人开发和维护车组代码（梯队+正队），时常出现有人搞不清楚最新的代码在哪，只能寄希望于师兄师姐，而师兄师姐自己也一头雾水的情况。**

​	**从技术的角度来看，车组代码脱胎于同一份代码框架，但是该框架设计之初并没有考虑设计一个可遵循的编程规范。这带来的问题是：框架类似，导致了全电控组范围内的“通用bug”；框架设计缺陷导致“通用bug”的解决无法快速复用到所有车组。解决这个问题的办法就是推出一套统一的、规范性强的架构，以及在电控组内推行一套统一的编程思想和范式。该点在此不做过多赘述。**

​	**从管理的角度来看，“通用型bug”由于技术缺陷而难以复用解决方案，容易让人产生畏难，或者说"畏烦"心理。有时候并不能一味地怪罪技术组，当务之急应是捋清楚技术组开发的根本障碍，并予以解决。像是车组内有人不知道最新代码是哪份，再进一步讲是车组没有形成规范的工作流，“什么时候需要改代码？改哪些部分？改动的时候需要通知其他组员……”诸如此类一概不知，仅凭借朴素的经验进行开发和交流，甚至有时候改动者面对文件管理器里若干个名称相似的文件夹一头雾水，分不清版本先后的例子时有发生，称之为“盲目”并不为过（叠甲，笔者之前也是个“盲目”的人）。笔者认为，这些现象只是某些本质问题的表征，解决代码管理，形成既定的规范和习惯才能缓解这些问题。**

​	**有人说：“不知道最新代码在哪里 == 近期很少关心车组事宜”，该说法有足够的道理，但也足够的片面，甚至不能解决任何问题。笔者认为，开发者好的开发习惯和责任心固然重要，但再怎么负责的人也会有缺乏沟通的时候，将代码质量与稳定性完全寄托于个人行为是一件不可靠的事情。与其说靠个别人孜孜不倦地“教诲”，不如规范一个工作流，大家都按照既定规则去协同开发，问题说不定更好把握呢？**

​	**当然，如果说该指南所述的开发流程对解决开发混乱的情况没有起到明显作用，就说明笔者给出的解决方案并不完美，但笔者坚持上述论断不变。抛开其他目的不谈，学习它，对个人技术的提升是肯定且有意义的，更何况这并不需要花多长时间，笔者的目的之一是想通过架构和代码管理的方式，让大家从全局的角度去思考一个工程的构建和维护。大家两年后回头看这份文档，可能会觉得很幼稚，但它一定比现在要成熟。**

**2025/7/1	余浩**
